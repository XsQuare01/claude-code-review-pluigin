# 공통 리뷰 규칙

이 문서는 모든 리뷰 모듈보다 먼저 적용하는 최상위 규칙입니다. 아래 항목은 개별 모듈보다 우선합니다.

이 리뷰 체계는 **React 애플리케이션 전용**입니다. 각 모듈은 자신이 전제하는 추가 스택(FSD, Electron, Tailwind 등)을 문서 상단에 명시하며, 해당 전제가 없는 프로젝트에서는 그 모듈을 적용하지 않습니다.

## Severity 기준

| Severity | 의미 |
|----------|------|
| 🔴 ERROR | 리뷰 기준 위반, 워크플로우 차원의 필수 수정 |
| 🟡 WARNING | 규칙 이탈, 문서/표현/운영 방식 보완 필요 |
| 🔵 INFO | 일관성 개선 제안 |

하위 모듈은 각자 더 구체적인 Severity 정의를 가질 수 있으며, 세부 판단은 **해당 모듈의 Severity 기준**을 우선 따른다.

---

## 00-1. 리뷰 중 mock / test 추가 금지 🔴

- 리뷰를 통과시키기 위해 새 mock 파일, mock 데이터, 임시 stub을 추가하면 위반
- 리뷰를 통과시키기 위해 `__test__`, `__tests__`, `*.test.*`, `*.spec.*` 파일을 새로 추가하면 위반
- 실제 요구사항이 아니라 "리뷰 대응용" 테스트/목 객체 추가는 금지

리뷰 시 이 패턴이 보이면 "문제 해결"이 아니라 "리뷰 우회" 가능성으로 간주하세요.

## 00-2. 규칙 ID 표기 🔴

모든 지적은 **파일 prefix와 일치하는 규칙 ID**를 달아야 한다.

| 모듈 종류 | ID 형식 | 예시 |
|-----------|---------|------|
| 숫자 prefix 모듈 | `{파일번호}-{규칙번호}` | `01-3`, `03-1`, `14-2`, `20-4` |
| 개발 원칙 (`10-principles.md`) | `10-{원칙 약어}` | `10-SSOT`, `10-DRY` |
| `exception.md` | `EX-{번호}` | `EX-1` |
| `props.md` | `P-{번호}` | `P-3` |
| `math.md` | `A-{번호}` / `C-{번호}` | `A-1`, `C-4` |

문서 안의 규칙 번호와 리포트의 규칙 ID는 항상 같아야 한다. 새 규칙을 추가할 때도 파일 prefix를 그대로 이어 붙인다.

## 00-3. 리뷰 범위 🔴

- 지적은 **diff에 포함된 변경 라인** 또는 그 변경 때문에 직접 깨진 **인접 라인/구조**에만 한정한다
- 전체 파일을 읽는 것은 **컨텍스트 파악용**일 뿐, 리뷰 범위를 파일 전체로 넓히는 근거가 아니다
- 사용자가 명시적으로 범위를 넓히라고 하지 않는 한 저장소 전체 스캔은 하지 않는다
- 다음 경로는 일반 리뷰 대상에서 제외한다: `__test__/**`, `__tests__/**`, `*.test.*`, `*.spec.*`, `__mocks__/**`, `mock/**`, `mocks/**`, `*.mock.*`, 테스트/목 전용 fixture

## 00-4. 네이밍 규칙 준수 🔴

- 파일명, 폴더명, 공개 API 이름은 역할이 바로 드러나야 함
- 같은 개념을 여러 이름으로 부르면 위반 (`user`, `userData`, `currentUser` 혼용 등)
- workflow/문서/리뷰 결과물 이름도 합의된 규칙을 따라야 함

## 00-5. 리뷰 문서 생성 규칙 🔴

- 모든 리뷰 워크플로우는 최종 결과를 기본적으로 `.md` 파일로 생성해야 함
- **예외**: 사용자가 read-only 리뷰, 파일 생성/수정 금지, 텍스트 응답만을 요청했으면 파일을 만들지 않는다. 이 요청은 이 규칙보다 우선한다 (00-9)
- 저장 기본 위치는 `./review-reports/`
- 파일명 규칙은 **`code-review-{workflow-name}-{branch-name}-{date}.md`** 로 고정한다. `workflow-name`을 생략하지 않는다
- 현재 정의된 workflow-name: `default`, `full`, `fast`, `commit`, `props`, `math`, `exception`
- 기존 리뷰 문서가 이미 있어도 그것을 완료 신호로 간주해 리뷰를 건너뛰지 않는다. 항상 **새 리뷰를 수행하고 새 문서를 생성**한다
- 리뷰 완료 후에는 사용자에게 저장 경로를 함께 보고한다

## 00-6. 문서/리포트 표현 규칙 🟡

- 리뷰 결과, 코멘트, 최종 리포트는 사용자가 다른 언어를 명시하지 않는 한 **한국어로 작성**한다
- 문서는 장황한 구현 설명보다 **해당 브랜치/커밋의 핵심 변경점과 이유**를 우선
- 같은 의미 반복 금지
- 긴 diff 나열보다 읽는 사람이 바로 판단할 수 있는 요약 우선
- 리뷰 코멘트는 가능하면 **문제 → 의도/현재 선택 → 왜 부족한지 → 개선 방향** 순서로 적는다
- 문서는 저장소 전체 일반론보다 **이번 브랜치에서 실제로 바뀐 파일, 흐름, 영향 범위** 중심으로 쓴다

## 00-7. 운영 규칙 🟡

- lint는 **읽기 전용으로 실행**해 남은 문제를 파악하고, 리뷰는 그 결과를 참고해 수행한다. 자동 수정은 사용자가 명시적으로 요청했을 때만 실행한다 (00-9)
- import만 맞다고 통과시키지 말고, 파일 위치/레이어 책임/네이밍까지 함께 검토
- "편해서 shared/common에 둠" 같은 임시 배치는 위반 후보로 본다
- 코드가 동작하더라도 **왜 이 선택을 했는지, 더 단순하거나 더 표준적인 대안 대비 정당한지** 함께 검토한다

## 00-8. 확장 메모 🔵

- 이후 추가되는 공통 리뷰 규칙도 이 문서에 계속 누적
- 개별 모듈과 충돌하면 이 문서의 규칙을 우선 적용
- 새 숫자 모듈을 추가할 때는 비어 있는 번호를 쓰지 말고 주제 순서에 맞는 위치에 넣은 뒤, 참조하는 모든 문서의 cross-reference를 함께 갱신한다

## 00-9. 실행 안전 계약 🔴

**모든 리뷰 워크플로우는 기본적으로 read-only다.** 리뷰는 코드를 판단하는 작업이지 코드를 바꾸는 작업이 아니다. 사용자가 리뷰를 요청했다는 사실은 파일 수정 권한을 준 것이 아니다.

이 계약은 모든 워크플로우(`default`, `full`, `fast`, `commit`, `props`, `math`, `exception`)에 동일하게 적용되며, 각 워크플로우 문서가 이와 다른 지시를 담고 있으면 **이 규칙이 우선**한다.

### 허용되는 실행

- 읽기: `git diff`, `git log`, 파일 읽기, 디렉터리 나열
- 비파괴 실행: lint/typecheck/test를 **수정 옵션 없이** 실행 (`--fix` 없이)

### 명시적 요청이 있어야 하는 실행

- lint/formatter 자동 수정 (`lint:fix`, `--fix`, `--write`)
- 리뷰 지적에 대한 코드 수정
- 리뷰 문서 파일 생성 이외의 파일 쓰기

자동 수정이 필요해 보이면 실행하지 말고, **무엇을 자동 수정할 수 있는지 리뷰 결과에 적어 사용자가 선택하게 한다.**

### 사용자 요청의 우선순위

사용자가 다음 중 하나를 말했으면 **다른 모든 규칙보다 우선**한다. 00-5의 리뷰 문서 생성 규칙도 여기에 밀린다.

- `read-only`, `읽기 전용`, `파일 수정하지 마`, `no file changes`, `text only`, `텍스트로만`

이 경우 리뷰 문서를 포함해 **어떤 파일도 만들거나 고치지 않고** 결과를 응답으로만 출력한다.

### 실행 결과의 보고 위치

lint/typecheck/test를 실행했으면 그 결과는 **리뷰 지적과 섞지 않고 별도 섹션으로 보고**한다. 도구가 잡은 것과 리뷰어가 판단한 것은 성격이 다르고, 섞이면 어느 쪽이 사람의 판단인지 구분되지 않는다.

```markdown
## 도구 실행 결과
| 명령 | 결과 | 비고 |
|------|------|------|
| `pnpm lint` | 실패 (12건) | 자동 수정 가능 9건 — 미실행 |
| `pnpm typecheck` | 통과 | |
```
