# 공통 리뷰 규칙

이 문서는 모든 리뷰 모듈보다 먼저 적용하는 최상위 규칙입니다. 아래 항목은 개별 모듈보다 우선합니다.

이 리뷰 체계는 **React 애플리케이션 전용**입니다. 각 모듈은 자신이 전제하는 추가 스택(FSD, Electron, Tailwind 등)을 문서 상단에 명시하며, 해당 전제가 없는 프로젝트에서는 그 모듈을 적용하지 않습니다.

## Severity 기준

지적의 severity는 **영향도 × 확신도** 두 축에서 파생한다. 영어로는 `impact × confidence` 파생이다.

규칙마다 등급을 고정하면 그 규칙을 위반한 인스턴스는 아무리 사소해도 같은 등급으로 나온다. 사실이지만 고칠 필요가 없는 지적이 🔴을 차지하고, 그런 리포트는 읽는 사람이 등급을 믿지 않게 만든다. 등급은 규칙이 아니라 **지적**이 갖는다.

### 영향도 — 고치지 않고 머지하면 무엇이 일어나는가

**높음** — 다음 중 하나를 지목할 수 있을 때만 해당한다. 이 닫힌 목록의 다섯째 항목은 `external-breakage`다.

- 사용자에게 보이는 오동작 또는 사용 불가 (`사용자에게 보이는 오동작 또는 사용 불가`) — 화면은 멀쩡해 보여도 사용자가 기능을 조작할 수 없게 되는 경우까지 포함한다. 키보드 트랩, 레이블 없는 컨트롤처럼 `12-accessibility.md`가 막는 접근성 차단이 여기 해당한다
- 데이터 손상·유실 (`데이터 손상·유실`)
- 보안 노출 (`보안 노출`)
- 빌드·타입체크·테스트 실패 (`빌드·타입체크·테스트 실패`)
- 빌드 밖 계약/복구 경로 파손 (`빌드 밖 계약/복구 경로 파손`) — 다른 코드베이스가 소비하는 계약을 깨거나(`16-api-contract.md` 16-5~16-7: 응답 필드 제거, 상태 코드 변경, IPC 채널명·환경 변수 키 변경), 롤백·복구 경로를 잃는 것(`18-dangerous-change.md` 18-2)

**낮음** — 위 어느 것도 지목할 수 없을 때. 스타일, 일관성, 이론적 비효율, 취향은 전부 낮음이다.

**목록은 닫혀 있다.** 무언가를 높음으로 올리려면 다섯 항목 중 하나를 이름 대야 한다. "유지보수성이 나빠진다", "나중에 문제가 될 수 있다"로는 올릴 수 없다. 다섯째 항목도 "이 저장소 밖에 영향이 있다"는 일반론이 아니라 **깨진 계약이나 잃은 복구 경로를 구체적으로 지목**할 때만 성립한다.

### 확신도 — 이 지적이 사실인가

**높음** — 해당 코드를 읽었고, 반례가 될 방어 장치가 없음을 함께 확인했다. 00-11이 요구하는 기준과 같다.

**낮음** — 그 외 전부. 패턴 기반 추정이거나, 확인하지 못한 경로가 남은 경우.

**00-11이 확신 낮음보다 우선한다.** 부재·가능성 주장인데 확인 범위가 diff를 넘지 못했으면 확신 낮음으로 등급을 매기지 말고 00-11대로 지적 대신 `확인 필요`로 적는다. 확신 낮음은 지적 자체는 성립하는 나머지 경우 — 부재 주장이 아니거나, 부재는 확인했고 다른 전제가 추정에 기대는 경우 — 에만 쓴다.

### 파생

| | 확신 높음 | 확신 낮음 |
|---|---|---|
| **영향 높음** | 🔴 | 🟡 |
| **영향 낮음** | 🟡 | 🔵 |

| Severity | 의미 |
|----------|------|
| 🔴 ERROR | 머지 전 반드시 고친다 |
| 🟡 WARNING | 머지를 막지 않으나 확인이 필요하다 |
| 🔵 INFO | 참고 |

각 축은 2단계다. "중간"을 두면 판정이 그리로 도피하고, 등급 부풀리기는 정확히 그 틈에서 생긴다.

🟡은 성격이 다른 두 가지를 담는다 — "중요한데 불확실"과 "확실한데 사소함". 두 축이 지적 바로 아래 줄에 적히므로 리포트에서 구분된다.

**이 파생 규칙은 계약 차원이며 모듈이 재정의하지 않는다.** 모듈이 정할 수 있는 것은 자기 도메인에서 무엇이 **영향 높음**에 해당하는가의 판정 기준이다.

**파생은 모든 워크플로우를 구속한다.** 어느 워크플로우가 만든 지적이든 두 축을 판정하고 severity는 그 파생으로만 정한다. 🔴 부풀리기를 막는 것은 이 판정이지 표기가 아니므로, 표기 형식이 다르다고 해서 판정이 면제되는 워크플로우는 없다.

**두 축을 적을 자리가 없는 출력 형식도 예외가 아니다.** 그 경우 두 축은 리포트에 **표시되지 않을 뿐, 어떤 등급을 고를지는 그대로 지배한다.** 표시 여부가 달라지면 리포트만 보고 등급을 검증할 수 있는지가 달라질 뿐이고, 등급 자체가 규칙 고정값으로 돌아가지는 않는다. 어느 형식이 두 축을 표시하는지는 `workflow-contract.md`의 **지적 표기**가 정한다.

하위 모듈은 자기 도메인에서 **어떤 사실이 영향 높음 근거가 되는지** 더 구체적으로 적을 수 있다. 하지만 최종 severity는 언제나 이 문서의 **영향도 × 확신도 파생**으로만 정한다. 모듈 문서는 영향 판정의 증거를 보정할 수 있을 뿐, 등급 자체를 올리거나 덮어쓰지 않는다.

구조화된 V1 manifest, producer ownership, validation lifecycle은 `workflow-contract.md`가 정본이다. 이 문서는 severity의 **전역 판정 규칙**만 정의한다.

### 규칙 문서의 이모지

규칙 헤딩의 이모지(`## 03-1. Hooks 규칙 🔴`)는 그 규칙 위반이 **대체로** 어느 영향도에 해당하는지의 참고 표시다. 지적의 severity는 위 파생으로만 정해지며, **규칙 표기가 파생을 덮어쓰지 않는다.**

표기와 실제 파생이 반복해서 어긋나면 그 규칙의 기본값이 틀렸다는 뜻이다. 규칙을 고칠 근거로 삼는다.

## 00-1. 테스트 정책 🔴

금지 대상은 **테스트 자체가 아니라 리뷰를 통과하기 위한 테스트**다. 둘을 구분하지 않고 테스트 추가를 일괄 금지하면 정상적인 회귀 방지 장치까지 막게 되고, 그것은 리뷰가 코드 품질을 떨어뜨리는 경우가 된다.

### 위반 — 리뷰 우회 신호

- 지적을 덮기 위해 assertion이 사실상 없는 테스트를 추가 (`expect(true).toBe(true)`, 호출만 하고 결과를 보지 않음)
- 검증 대상 로직 자체를 mock으로 대체해 실제로는 아무것도 검증하지 않는 테스트
- production dependency를 우회하는 mock으로 실패 경로를 가림
- 지적된 코드는 그대로 두고 테스트만 추가해 "확인됨"으로 처리

이 패턴이 보이면 "문제 해결"이 아니라 **리뷰 우회 가능성**으로 간주한다.

### 위반 아님 — 정상적인 테스트 작업

- 변경된 동작을 실제로 검증하는 테스트 추가·수정
- 구체적인 회귀 경로가 있어 그것을 고정하는 테스트
- 기존 테스트가 변경된 동작과 어긋나 함께 갱신되는 경우

### 리뷰어의 테스트 취급

- **변경된 테스트는 영향 범위의 증거로 읽는다.** 어떤 동작이 바뀌었는지, 어떤 경계 조건을 의도했는지가 테스트 diff에 드러난다
- 구체적인 회귀 경로를 지목할 수 있으면 테스트 추가를 **권고**할 수 있다. 경로를 지목하지 못하면 권고하지 않는다
- **테스트 부재만으로 자동 위반을 만들지 않는다.** 다만 사용자 데이터·결제·삭제·외부 부작용에 직접 닿는 변경에 안전 증거가 전혀 없으면 지적한다
- 커버리지 숫자를 근거로 지적하지 않는다

## 00-2. 규칙 ID 표기 🔴

모든 지적은 **파일 prefix와 일치하는 규칙 ID**를 달아야 한다.

| 모듈 종류 | ID 형식 | 예시 |
|-----------|---------|------|
| 숫자 prefix 모듈 | `{파일번호}-{규칙번호}` | `01-3`, `03-1`, `14-2`, `20-4` |
| 개발 원칙 (`10-principles.md`) | `10-{원칙 약어}` | `10-SSOT`, `10-DRY` |
| `exception.md` | `EX-{번호}` | `EX-1` |
| `props.md` | `P-{번호}` | `P-3` |
| `math.md` | `A-{번호}` / `C-{번호}` | `A-1`, `C-4` |
| `agents/correctness-reviewer.md` | `CR-{번호}` | `CR-1` |

correctness 패스는 규칙 문서가 아니라 PR 의도를 근거로 지적하므로 **자기 namespace를 쓴다.** 규칙 모듈 ID를 빌려 쓰면 리포트를 읽는 사람이 규칙 문서에서 근거를 찾다가 실패한다.

문서 안의 규칙 번호와 리포트의 규칙 ID는 항상 같아야 한다. 새 규칙을 추가할 때도 파일 prefix를 그대로 이어 붙인다.

**같은 ID로 지적이 둘 이상이면 순번을 붙인다** — `17-3 (1/2)`, `17-3 (2/2)`. 순번이 없으면 "`17-3` 고쳤나?"라는 질문에 어느 것인지 답할 수 없다. 하나뿐이면 붙이지 않는다.

## 00-3. 리뷰 범위 🔴

- 지적은 **diff에 포함된 변경 라인** 또는 그 변경 때문에 직접 깨진 **인접 라인/구조**에만 한정한다
- 전체 파일을 읽는 것은 **컨텍스트 파악용**일 뿐, 리뷰 범위를 파일 전체로 넓히는 근거가 아니다
- 사용자가 명시적으로 범위를 넓히라고 하지 않는 한 저장소 전체 스캔은 하지 않는다
- 다음 경로는 **지적 대상**에서 제외한다: `__test__/**`, `__tests__/**`, `*.test.*`, `*.spec.*`, `__mocks__/**`, `mock/**`, `mocks/**`, `*.mock.*`, 테스트/목 전용 fixture
- 제외의 의미는 "테스트 파일의 스타일·구조를 지적하지 않는다"이지 "테스트 변경을 보지 않는다"가 아니다. **변경된 테스트는 production 코드 변경의 영향 범위를 읽는 증거로 활용한다** (00-1)
- 예외: 테스트가 리뷰 우회 신호에 해당하면(00-1) 그 자체를 지적한다

## 00-4. 네이밍 규칙 준수 🔴

- 파일명, 폴더명, 공개 API 이름은 역할이 바로 드러나야 함
- 같은 개념을 여러 이름으로 부르면 위반 (`user`, `userData`, `currentUser` 혼용 등)
- workflow/문서/리뷰 결과물 이름도 합의된 규칙을 따라야 함

## 00-5. 리뷰 문서 생성 규칙 🔴

- 모든 리뷰 워크플로우는 최종 결과를 기본적으로 `.md` 파일로 생성해야 함
- **예외**: 사용자가 read-only 리뷰, 파일 생성/수정 금지, 텍스트 응답만을 요청했으면 파일을 만들지 않는다. 이 요청은 이 규칙보다 우선한다 (00-9)
- 저장 기본 위치는 `./review-reports/`
- 파일명 규칙은 **`code-review-{workflow-name}-{branch-name}-{date}.md`** 로 고정한다. `workflow-name`을 생략하지 않는다
- 현재 정의된 workflow-name: `default`, `full`, `fast`, `commit`, `props`, `math`, `exception`
- 기존 리뷰 문서가 이미 있어도 그것을 완료 신호로 간주해 리뷰를 건너뛰지 않는다. 항상 **새 리뷰를 수행하고 새 문서를 생성**한다
- 리뷰 완료 후에는 사용자에게 저장 경로를 함께 보고한다

## 00-6. 문서/리포트 표현 규칙 🟡

- 리뷰 결과, 코멘트, 최종 리포트는 사용자가 다른 언어를 명시하지 않는 한 **한국어로 작성**한다
- 문서는 장황한 구현 설명보다 **해당 브랜치/커밋의 핵심 변경점과 이유**를 우선
- 같은 의미 반복 금지
- 긴 diff 나열보다 읽는 사람이 바로 판단할 수 있는 요약 우선
- 리뷰 코멘트는 가능하면 **문제 → 의도/현재 선택 → 왜 부족한지 → 개선 방향** 순서로 적는다
- 문서는 저장소 전체 일반론보다 **이번 브랜치에서 실제로 바뀐 파일, 흐름, 영향 범위** 중심으로 쓴다

- 공통 생산자 문맥의 불변식은 **경로/줄번호/코드 인용을 추측하지 않는다**는 점이다. 위치·렌더링의 표현 형식은 `workflow-contract.md`가 소유하고, 이 문서는 workflow-neutral 판단 규칙만 제공한다

### 다른 언어를 요청받았을 때

리포트 골격은 한국어 섹션 이름으로 고정돼 있다(`workflow-contract.md` C-7). 사용자가 다른 언어를 요청하면 골격이 바뀌므로, 무엇이 바뀌고 무엇이 남는지 미리 정해 둔다.

| | 대상 |
|---|---|
| **번역한다** | 섹션 이름, 지적 본문, 판정·요약, `SKIPPED`·`UNKNOWN` 사유 서술 |
<!-- PUBLIC_OUTPUT_LOCATION_LITERAL_ALLOW:BEGIN -->
| **번역하지 않는다** | 규칙 ID(`03-1`, `CR-2`), 파일 경로, 코드 인용, Severity 표기, 두 축 표기(`영향`·`확신`과 그 값 `높음`·`낮음`), 상태 토큰(`SKIPPED`, `UNKNOWN`, `위치 미확인`, `확인 필요`, `버전 미확인`) |
<!-- PUBLIC_OUTPUT_LOCATION_LITERAL_ALLOW:END -->

- 상태 토큰을 번역하면 두 리포트를 기계적으로 비교할 수 없다. 골격을 고정한 이유가 그것이고(C-7), 언어가 바뀌어도 그 이유는 그대로다
- 리포트의 `리뷰 기준` 섹션에 **사용한 언어를 적는다.** 같은 워크플로우의 두 리포트가 서로 다른 섹션 이름을 갖게 되는데, 그것이 골격 위반이 아니라 요청 결과임을 리포트만 보고 알 수 있어야 한다

## 00-7. 운영 규칙 🟡

- lint는 **읽기 전용으로 실행**해 남은 문제를 파악하고, 리뷰는 그 결과를 참고해 수행한다. 자동 수정은 사용자가 명시적으로 요청했을 때만 실행한다 (00-9)
- import만 맞다고 통과시키지 말고, 파일 위치/레이어 책임/네이밍까지 함께 검토
- "편해서 shared/common에 둠" 같은 임시 배치는 위반 후보로 본다
- 코드가 동작하더라도 **왜 이 선택을 했는지, 더 단순하거나 더 표준적인 대안 대비 정당한지** 함께 검토한다

## 00-8. 확장 메모 🔵

- 이후 추가되는 공통 리뷰 규칙도 이 문서에 계속 누적
- 개별 모듈과 충돌하면 이 문서의 규칙을 우선 적용
- 새 숫자 모듈은 **다음 빈 번호에 덧붙이고 기존 모듈을 재번호하지 않는다.** 규칙 ID는 리뷰 리포트에 인용되므로 재번호는 과거 리포트의 추적성을 끊는다. 주제별 묶음보다 ID 안정성을 우선한다
- 모듈을 추가하면 같은 변경에서 README 인벤토리와 `fast.md`의 해당 섹션을 함께 갱신한다

## 00-9. 실행 안전 계약 🔴

**모든 리뷰 워크플로우는 기본적으로 read-only다.** 리뷰는 코드를 판단하는 작업이지 코드를 바꾸는 작업이 아니다. 사용자가 리뷰를 요청했다는 사실은 파일 수정 권한을 준 것이 아니다.

이 계약은 모든 워크플로우(`default`, `full`, `fast`, `commit`, `props`, `math`, `exception`)에 동일하게 적용되며, 각 워크플로우 문서가 이와 다른 지시를 담고 있으면 **이 규칙이 우선**한다.

### 허용되는 실행

- 읽기: `git diff`, `git log`, 파일 읽기, 디렉터리 나열
- 비파괴 실행: lint/typecheck/test를 **수정 옵션 없이** 실행 (`--fix` 없이)

### 명시적 요청이 있어야 하는 실행

- lint/formatter 자동 수정 (`lint:fix`, `--fix`, `--write`)
- 리뷰 지적에 대한 코드 수정
- 리뷰 문서 파일 생성 이외의 파일 쓰기

자동 수정이 필요해 보이면 실행하지 말고, **무엇을 자동 수정할 수 있는지 리뷰 결과에 적어 사용자가 선택하게 한다.**

### 사용자 요청의 우선순위

사용자가 다음 중 하나를 말했으면 **다른 모든 규칙보다 우선**한다. 00-5의 리뷰 문서 생성 규칙도 여기에 밀린다.

- `read-only`, `읽기 전용`, `파일 수정하지 마`, `no file changes`, `text only`, `텍스트로만`

이 경우 리뷰 문서를 포함해 **어떤 파일도 만들거나 고치지 않고** 결과를 응답으로만 출력한다.

### 실행 결과의 보고 위치

lint/typecheck/test를 실행했으면 그 결과는 **리뷰 지적과 섞지 않고 별도 섹션으로 보고**한다. 도구가 잡은 것과 리뷰어가 판단한 것은 성격이 다르고, 섞이면 어느 쪽이 사람의 판단인지 구분되지 않는다.

```markdown
## 도구 실행 결과
| 명령 | 결과 | 비고 |
|------|------|------|
| `pnpm lint` | 실패 (12건) | 자동 수정 가능 9건 — 미실행 |
| `pnpm typecheck` | 통과 | |
```

## 00-10. 위치 표기 🔴

**틀린 위치를 가리키는 지적은 지적이 아니다.** 읽는 사람은 그 줄로 가서 아무 관련 없는 코드를 보고, 그 시점부터 리포트 전체를 의심하기 시작한다. 실제로 이 재작업이 리뷰 시간의 7%를 차지한 적이 있다.

이 규칙은 각 모듈의 출력 형식표보다 우선하며, **모든 모듈의 모든 지적에 적용**된다.

### 표기 형식

- `경로:줄번호` — 경로는 저장소 루트 기준 (`src/features/auth/login.tsx:42`)
- 범위는 `path:12-18`
- 삭제된 코드를 가리킬 때는 변경 전 기준임을 명시한다 (`(삭제 전) path:L40`)

### 번호를 구하는 방법

- 줄번호는 **변경 후 파일**(diff의 `+` 쪽) 기준이다
- **diff hunk 헤더(`@@ -a,b +c,d @@`)에서 계산하지 않는다.** 해당 파일을 실제로 읽어 확인한 번호를 적는다. 계산으로 낸 번호는 hunk가 여러 개일 때, 컨텍스트 줄이 섞일 때, 같은 파일에 삭제와 추가가 함께 있을 때 어긋난다
- 위치를 확인할 수 없으면 번호를 추측하지 않는다. Structured producer는 `location.kind = "unverified"`와 `reason`만 사용하고 `path`, `line`, `lineBefore`, `quote`를 꾸며 넣지 않는다. 공개 렌더링 표현과 legacy/direct 출력 토큰은 `workflow-contract.md`가 소유한다. **추측한 번호는 확인되지 않은 지적보다 나쁘다** — 확인되지 않았다는 사실이 감춰지기 때문이다

### 인용을 함께 붙인다

지적마다 그 위치의 **실제 코드를 한 줄 인용**한다.

```
🔴 | 04-1 | src/features/chat/use-room.ts:28 | `useEffect(() => { connect(roomId) }, [])`
```

인용은 두 가지를 동시에 해결한다. 번호가 틀렸을 때 인용문이 그 줄과 맞지 않아 **즉시 드러나고**, 인용을 쓰려면 그 줄을 읽어야 하므로 **애초에 틀릴 일이 줄어든다.** 인용 없이 번호만 적은 지적은 검증할 방법이 없다.

### 범위를 벗어난 지적 방지

00-3이 리뷰 범위를 정한다. 인접 구조를 지적할 때는 **그 변경 때문에 어떻게 깨졌는지**를 함께 적는다. 그 문장을 쓸 수 없으면 diff 밖 일반론이므로 지적하지 않는다.

## 00-11. 부재 주장의 근거 🔴

리뷰 지적의 상당수는 **무언가가 없다**는 주장이다 — "cleanup이 없다", "guard가 없다", "검증이 없다", "경쟁 조건이 가능하다". 이 형태는 **확인하지 않고도 쓸 수 있고, 쓰고 나면 확인한 것처럼 읽힌다.** 있는 것을 지적하려면 그것을 찾아야 하지만, 없는 것을 지적하는 데는 찾지 않는 것으로 충분하기 때문이다.

실제로 이 저장소의 리뷰 실행에서 세 모듈이 "경쟁 상태 가능", "특정 데이터 경로 위험"을 지적했다가 정정 단계에서 전부 폐기됐다. 사유는 동일했다 — **방어 장치가 실제로는 있었다.** 폐기하는 데도 시간이 들었고, 폐기되지 않았다면 존재하지 않는 문제를 고치는 데 시간이 들었을 것이다.

"추측하지 마라"는 이미 00-3과 각 워크플로우 출력 원칙에 있다. 그런데도 발생했다. **금지만으로는 부족하고, 확인했다는 사실이 지적에 남아야 한다.**

### 요구사항

부재나 가능성을 주장하는 지적에는 **무엇을 확인했는지**를 함께 적는다.

| 형태 | 판정 |
|------|------|
| "cleanup이 없어 구독이 누수된다" | 🔴 근거 없음 — 어디를 봤는지 알 수 없다 |
| "effect 본문과 return을 확인했고 cleanup이 없다" | ✅ 확인 가능 |
| "경쟁 조건이 가능하다" | 🔴 반증 불가능한 서술 |
| "결과를 `setState`로 반영하는데 abort·ignore·token 중 어느 것도 없다" | ✅ 무엇이 없는지 특정됨 |

### 판정 기준

- **방어 장치가 없다고 주장하려면, 그 흐름에서 가능한 방어 수단을 어디까지 찾아봤는지** 적는다. 상위 컴포넌트나 라우터 레벨의 guard가 있는데 못 본 경우가 가장 흔하다
- 확인 범위가 diff로 한정돼 그 밖의 방어 여부를 모르면, 지적 대신 **`확인 필요`로 적고 무엇을 확인해야 하는지** 쓴다. 이건 약한 지적이 아니라 정직한 지적이다. **이 조항이 Severity 기준의 `확신 낮음`보다 우선한다** — 그 경우는 확신 낮음 지적으로 만들지 않는다
- 이 요구는 위치 표기(00-10)와 함께 적용된다. 인용이 "그 줄이 실제로 그렇다"를 보이는 것이라면, 이 규칙은 **"찾아봤는데 없다"를 보이는 것**이다
