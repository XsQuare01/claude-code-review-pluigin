# 개발자 경험(DX) 검증

이 모듈은 코드가 "동작하는가"를 넘어서, 다른 개발자가 빠르게 이해하고 안전하게 수정할 수 있는지를 검토합니다.

단, FSD 역할 배치(`01-fsd.md`), 네이밍(`07-naming.md`), 상태 관리(`04-state.md`), 성능(`14-react-performance.md`)처럼 **다른 모듈이 더 직접적으로 다루는 영역**은 그쪽 모듈을 우선한다. 여기서는 DX 고유 영역(발견성, 수정 안전성, 진입점 명확성, 온보딩 비용)이 남는 경우만 본다.

## Severity 기준

| Severity | 의미 |
|----------|------|
| 🔴 ERROR | 변경 비용이 과도하게 커지고, 실수 유발 가능성이 높은 구조 |
| 🟡 WARNING | 탐색/수정/확장 속도를 떨어뜨리는 DX 저하 |
| 🔵 INFO | 온보딩, 발견성, 사용성 개선 제안 |

---

## 13-1. 발견성(Discoverability) 🔴

- 파일/폴더 이름만 보고 역할이 드러나지 않음
- public API를 열어도 "무엇을 어떻게 써야 하는지" 바로 파악되지 않음
- 비슷한 책임 코드가 여러 위치에 흩어져 첫 진입점이 모호함

## 13-2. 수정 안전성(Change Safety) 🔴

- 하나 수정에 여러 파일을 암묵적으로 함께 알아야 하는 구조
- side effect, 상태 변경, 외부 호출 경계가 숨겨져 영향 범위 예측이 어려움
- 동일 개념이 여러 이름/형태로 노출되어 잘못된 사용을 유도함

## 13-3. 사용 패턴 일관성 🟡

- 같은 기능군인데 생성/조회/변경 방식이 제각각
- 훅, 액션, selector, query key, IPC API의 호출 패턴이 일관되지 않음
- 새 코드를 작성할 때 "어느 패턴을 따라야 하는지" 예제가 보이지 않음

## 13-4. 문서화가 필요한 지점 🟡

다음은 짧은 주석/README/usage 예시가 있어야 합니다:

- 비자명한 진입 순서나 초기화 순서
- 왜 이런 구조인지 바로 이해되지 않는 workaround
- 외부에서 잘못 쓰기 쉬운 public API

반대로, 코드만 읽어도 명확한 내용의 장황한 설명은 지적하지 않습니다.

## 13-5. 온보딩 친화성 🟡

- 새 슬라이스/컴포넌트/훅을 어디에 추가해야 할지 구조만 보고 판단하기 어려움
- 비슷한 파일들의 segment 구조가 달라 복붙/확장이 어려움
- 필요한 상수, 타입, helper의 단일 출처가 없어 탐색 비용이 큼

## 13-6. 파일 위치 적합성 🟡

- 파일 내용과 현재 위치가 맞지 않아 첫 탐색 경로에서 발견되지 않음
- 재사용 가능한 코드가 지나치게 깊은 로컬 폴더에 숨어 있음
- 반대로 특정 화면/기능 전용 코드가 shared/common 위치에 올라가 있음
- 같은 성격의 파일들이 프로젝트 안에서 서로 다른 위치 규칙을 따름

## 13-7. 추출/재사용 판단 🔵

- 같은 구현 패턴이 2곳 이상 반복되는데 공용 진입점이 없음
- 팀 표준 유틸/헬퍼로 승격할 가치가 있는데 로컬 구현이 반복됨
- 반대로 너무 이른 추상화로 API가 불필요하게 복잡해진 경우도 지적

## 13-8. 리뷰 출력 원칙 🔵

- "어렵다"고만 쓰지 말고, 다음 개발자가 어디서 막히는지 구체적으로 설명
- 가능하면 "어디를 단일 진입점으로 삼을지" 또는 "어떤 이름/구조로 통일할지"까지 제안

## 13-OUTPUT. 출력 형식

<!-- REVIEW_RESULT_CONTRACT_V1_PRODUCER_OUTPUT -->

이 문서를 producer prompt에 쓸 때는 **`REVIEW_RESULT_CONTRACT_V1`** 을 따른다. 응답은 Markdown 표나 헤딩이 아니라 **raw JSON 객체 하나만** 반환한다.

- top-level에는 `schemaVersion`, `findings`, `openQuestions`를 항상 포함하고 `schemaVersion`은 `1`이어야 한다.
- `severity`는 producer가 내지 않는다. 이 모듈은 `impact`와 `confidence`만 판정한다.
- 발견성, 수정 안전성, 패턴 일관성, 온보딩 비용, 파일 위치 적합성 같은 도메인별 설명은 새 schema field를 만들지 말고 `body`, `recommendation`, `evidence`에 담는다.
- `00-rule.md` 00-11에 걸리는 unresolved absence/possibility claim, search scope 미완료, 추가 탐색 요청만 `openQuestions`로 보낸다.
- 결함은 성립하지만 exact location만 확인하지 못했으면 finding을 유지하고 `location.kind="unverified"`와 `reason`만 사용한다.
- producer 문자열 필드는 최종 리포트의 신뢰된 Markdown이 아니다. heading/table/raw HTML/link를 직접 만들려고 하지 말고 plain prose만 넣는다.
