# 삭제 회귀 점검

## 영향도 보정 예시

| 영향도 | 이 모듈에서 자주 보이는 근거 |
|----------|------|
| 높음 | 필요한 production code, contract path, cleanup, boundary가 실제로 사라져 사용자 오동작·검증 실패·외부 파손이 닫히는 경우 |
| 낮음 | 삭제 의도는 보이지만 이동·대체·정리 증거가 부족하거나, 회귀 가능성은 있으나 실제 파손 범주를 아직 닫지 못한 경우 |

단순 삭제 자체가 자동 높은 영향은 아니다. 어떤 동작이나 계약이 사라졌는지를 현재 변경에서 닫아 보여줄 때만 높음으로 둔다.

---

## 20-1. diff 삭제 항목 우선 확인 🔴

- `git diff`에서 제거된 파일과 `-` 라인을 먼저 본다.
- 삭제된 항목이 production export, function, type, constant, helper, runtime config, schema, API contract에 해당하면 회귀 가능성을 우선 의심한다.
- `__test__`, `__tests__`, `*.test.*`, `*.spec.*`, `__mocks__`, mock/mocks, fixture/mock data 전용 파일은 일반 리뷰 범위에서 제외한다 (`00-rule.md` 00-3).
- 삭제가 단순 정리인지, 실제 동작 제거인지 diff만으로 판단하지 말고 변경 전후 흐름까지 확인한다.

## 20-2. 아직 필요할 수 있는 production 코드 삭제 🔴

- production 코드 삭제는 자동으로 안전하다고 보지 않는다.
- 아래 중 하나라도 보이면 삭제 회귀로 본다.
  - 관련 기능이 여전히 유지되는데 구현/호출 경로만 사라짐
  - 공통 helper 삭제 후 동일 로직이 여러 파일로 흩어짐
  - schema/API/event/serialization 계약이 유지되는데 타입·상수·변환 코드만 사라짐
  - 삭제된 함수/타입의 대체 호출부 변경이 diff 안에 없음
- 코드가 이동/통합된 경우에는 새 위치와 대체 호출 경로가 diff 안에 보여야 한다.

## 20-3. 참조 확인 🔴

- 삭제된 export, function, type, constant가 여전히 참조되는지 확인한다.
- 직접 참조가 없더라도 다음이면 삭제를 경계한다.
  - 런타임 경로에서 여전히 필요함
  - 재사용성/공통 처리 역할을 잃어 다른 파일의 중복이 증가함
  - 숨은 계약(API, schema, 이벤트, 직렬화 포맷)을 깨뜨림
- 범위는 diff 기반으로 유지하고, 삭제된 파일/심볼에 한해 targeted reference check만 한다. 전체 저장소를 넓게 훑지 않는다.
- tests pass 여부만으로 삭제 안전성을 판단하지 않는다.

## 20-4. React 고유 삭제 회귀 🔴

React 코드에서는 다음 삭제가 겉보기에 무해해 보이지만 동작을 바꾼다.

- `useEffect` cleanup 반환문 삭제 → 구독·타이머 누수
- 의존성 배열 항목 삭제 → 재실행 누락, stale closure
- `key` prop 삭제 또는 값 변경 → 리스트 재마운트 또는 상태 오매칭
- `Suspense`/Error Boundary 경계 컴포넌트 삭제 → 하위 로딩·실패가 상위로 전파
- `memo`/`useMemo` 제거 자체는 대개 안전하지만, 그것에 의존하던 참조 동등성 로직이 함께 있는지 확인

## 20-5. 합법적 삭제와 회귀 삭제 구분 🟡

- 아래 증거가 있으면 합법적 삭제로 볼 수 있다.
  - 동일 책임의 코드가 다른 파일로 이동됨
  - 이름 변경/리네임/모듈 통합이 함께 이루어짐
  - 관련 호출부, import, export가 함께 갱신됨
  - 기능 제거가 제품 요구사항에 의해 명시됨
- 반대로, 삭제만 있고 대체/이관/설명 증거가 없으면 회귀 후보로 본다.

## 20-OUTPUT. 도메인 결과 가이드 🟡

- 단순히 "삭제됨"만 적지 말고, **무엇이 사라졌고 왜 아직 필요한지**를 설명한다.
- 이동·대체·호출부 갱신이 부족하다면 어느 새 위치나 대체 경로가 보여야 안전했는지를 적는다.
- cleanup, key, Suspense boundary 같은 React 고유 삭제 회귀는 **어떤 실패가 다시 드러나는지**까지 남긴다.

## 20-SCOPE. 중복 방지 🟡

- 삭제가 public contract 제거로 드러나면 `16-api-contract.md`의 versioning/deprecation 증거도 함께 확인한다.
- 삭제가 권한·데이터·과금 흐름에 닿으면 `18-dangerous-change.md` 쪽 **별도 finding 추가를 검토**하고, 두 축은 각 finding에서 독립 판정한다.
- `00-rule.md`의 mock / test 추가 금지와 충돌하지 않도록, 리뷰 중 새 mock/test 추가를 요구하지 않는다.

## 20-JUDGE. 판단 기준 요약 🔴

- 삭제된 것이 production code인지, 리뷰 제외 대상(test/mock 전용 자산)인지 먼저 분류한다.
- 대체 경로, 이동, 리네임, 호출부 수정이 함께 있는지 본다.
- 필요한데 사라진 항목이면 높은 영향 근거를 검토하고, 의도는 보이나 증거가 약하면 영향 낮음 쪽 근거로 남긴다. 명확한 정리는 대체로 영향 낮음 또는 생략이다.
