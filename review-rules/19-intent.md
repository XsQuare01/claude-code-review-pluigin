# 문제-의도-선택 근거 검증

이 모듈은 코드가 **왜 존재하는지**, **왜 이 방식으로 작성됐는지**, **그 선택이 현재 맥락에서 정당한지**를 검토한다. 단순히 동작 여부만 보지 않고, 문제 정의·설계 의도·트레이드오프·장기 변경 비용까지 함께 본다.

다음은 이 문서의 검사 범위가 아니다 (중복 방지):

- 순수 타입 문법 오류, import 누락, dead code → `02-type.md`, `09-code-quality.md`
- 레이어 위치 자체의 아키텍처 규칙 위반 → `01-fsd.md`
- 순수 알고리즘 Big-O 문제 → `15-performance.md`
- 원칙 이름 붙이기 → `10-principles.md`

여기서는 **"문제는 맞게 잡았는가 / 선택 이유가 드러나는가 / 미래 비용이 정당한가"** 를 본다.

## Severity 기준

| Severity | 의미 |
|----------|------|
| 🔴 ERROR | 문제 정의와 구현 선택이 어긋나 실제 운영/변경 시 큰 비용 또는 오동작 위험 |
| 🟡 WARNING | 의도·선택 근거가 불충분해 유지보수자가 잘못 이해하거나 과한 비용을 떠안을 가능성 |
| 🔵 INFO | 선택 이유·트레이드오프·대안 비교를 더 명확히 남기면 좋아지는 경우 |

## 19-1. 문제와 해결 방식이 어긋남 🔴

- 요구는 단순한데 과도한 추상화/범용화/설정화를 도입함
- 반대로 복잡한 문제인데 임시 우회 코드로 눌러두어 다음 변경에서 쉽게 깨짐
- 증상만 가렸고 원인이나 경계 조건은 그대로 남아 있음
- 호출자/사용자 문제를 풀어야 하는데 구현 편의 중심 API로 설계됨

## 19-2. 핵심 트레이드오프가 숨겨짐 🔴

- 성능, 단순성, 일관성, 확장성 중 하나를 크게 희생했는데 이유가 드러나지 않음
- 메모리를 더 써서 빠르게/복잡하게 짜서 일반화하는 선택을 했지만 그 근거가 없음
- strict한 검증 대신 관대한 허용을 택했는데 운영상 안전장치가 없음
- 비표준 패턴이나 workaround를 택했는데 왜 필요한지, 언제 제거할지 설명이 없음

## 19-3. 의도가 검증 가능하게 표현되지 않음 🟡

- 코드/이름/짧은 주석/리뷰 설명만으로 "왜 이 코드가 있는지" 파악되지 않음
- 함수/훅/유틸 이름은 일반적인데 실제 역할은 더 좁거나 더 위험함
- 중요한 분기나 예외 처리가 도메인 규칙인지 임시 방어인지 구분되지 않음
- 다음 개발자가 요구사항인지 구현 습관인지 구분할 근거가 없음

## 19-4. 더 단순한 대안 대비 선택 근거 부족 🟡

- 로컬 로직이면 충분한데 전역 상태/추상 레이어/설정 구조를 올림
- 사용처 하나인데 재사용 프레임워크처럼 설계함
- 표준 패턴으로 충분한데 커스텀 패턴을 도입하고도 얻는 이점이 불분명함
- React가 이미 제공하는 기본 동작(`key` 기반 리셋, 렌더 중 파생, Suspense)을 수동 구현으로 대체하고 근거가 없음
- 팀의 기존 패턴에서 벗어났는데 얻는 가치가 명확히 보이지 않음

## 19-5. 장기 변경 비용을 전가함 🟡

- 지금은 되지만 다음 수정자가 여러 암묵적 전제를 함께 알아야만 안전하게 바꿀 수 있음
- 확장 포인트처럼 보이는데 실제로는 한 곳만 위한 특수 규칙이 숨어 있음
- 이후 요구가 조금만 바뀌어도 같은 코드를 여러 군데 다시 손봐야 하는 구조임
- 리뷰어가 "왜 이 코드를 지워도 되는지" 또는 "어디까지 영향이 있는지" 판단하기 어려움

## 19-6. 선택 이유 명시 권장 🔵

- 복잡도, 캐시, debounce, batching, fallback, feature flag 선택 이유가 짧게라도 남아 있으면 좋음
- 일반적인 구현 대신 우회 경로를 택한 경우 제거 조건/재검토 시점을 남기면 좋음
- 성능보다 단순함을 택했거나, 단순함보다 확장성을 택했다면 그 우선순위를 드러내면 좋음

이 문서를 producer prompt에 쓸 때는 **`REVIEW_RESULT_CONTRACT_V1`** 을 따른다. 응답은 Markdown 표나 헤딩이 아니라 **raw JSON 객체 하나만** 반환한다.

- top-level에는 `schemaVersion`, `findings`, `openQuestions`를 항상 포함하고 `schemaVersion`은 `1`이어야 한다.
- `severity`는 producer가 내지 않는다. 이 모듈은 `impact`와 `confidence`만 판정한다.
- 문제/의도/선택, 왜 불충분한지, 더 단순한 대안이나 근거 보강 방향은 새 schema field를 만들지 말고 `body`, `recommendation`, `evidence`에 담는다.
- `00-rule.md` 00-11에 걸리는 unresolved absence/possibility claim, search scope 미완료, 추가 탐색 요청만 `openQuestions`로 보낸다.
- 결함은 성립하지만 exact location만 확인하지 못했으면 finding을 유지하고 `location.kind="unverified"`와 `reason`만 사용한다.
- producer 문자열 필드는 최종 리포트의 신뢰된 Markdown이 아니다. heading/table/raw HTML/link를 직접 만들려고 하지 말고 plain prose만 넣는다.

**원칙**
- "마음에 들지 않는다"고 쓰지 말고 **문제 → 현재 선택 → 왜 불충분한지 → 개선 방향** 순서로 적는다
- 작성자의 의도를 추측해 단정하지 말고, **코드/이름/주석/변경 설명에서 검증 가능한 근거**만 사용한다
- 의도가 나쁘다고 단정하기보다, **의도가 검증 가능하게 표현되지 않았다**고 지적한다
- 더 단순한 대안이 있으면 "무엇을 잃고 무엇을 얻는지"까지 같이 제안한다
