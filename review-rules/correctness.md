# Correctness Review — 의도 대비 구현

변경이 **하려는 일을 모든 경로에서 실제로 하는지**를 보는 전용 판정 문서. 규칙 모듈은 "이 코드가 규칙을 어기는가"를 묻고, 이 문서는 "이 코드가 변경이 약속한 동작을 하는가"를 묻는다. `/code-review-full --correctness on`의 정확성 패스에서 쓰이고, 직접 호출하는 `agents/correctness-reviewer.md`도 같은 판정 기준을 쓴다. 파일명에 숫자 prefix가 없으므로 일반 모듈 스캔에서 제외된다.

**지적 ID는 `CR-{번호}`다.** 번호는 이 패스가 낸 지적의 순번이고 **규칙 조항이 아니다.** 이 문서에는 `CR-1` 같은 조항이 없으며, 만들지 않는다. 지적의 근거는 규칙 문장이 아니라 변경의 의도와 코드 경로다. 규칙 모듈의 ID(`03-1` 등)를 빌려 쓰지 않는다 — 리포트를 읽는 사람이 규칙 문서에서 근거를 찾다가 실패한다.

## 무엇을 근거로 의도를 정하는가

의도는 아래 중 **실제로 받은 것**으로만 정하고, 어디서 왔는지를 지적에 적는다.

| 출처 | 쓰는 법 |
|------|---------|
| PR 제목·설명 | 의도의 정본이다 |
| 사용자가 리뷰를 요청하며 적은 요구 | PR 설명이 없을 때의 정본이다 |
| 커밋 메시지 | **의도 추정**이다. 그렇게 적는다 |
| 코드 자체 | 의도가 아니라 **확인한 사실**이다. 코드만으로 의도를 지어내지 않는다 |

PR 설명이 없으면 코드에서 확인한 사실과 의도 추정을 구분해 쓴다. "이 함수는 X를 하려는 것 같다"는 사실이 아니다 — 그 추정에 기댄 지적은 확신을 낮추거나 추가 확인 항목으로 내린다.

## 어느 경로를 따라가는가

변경된 입력에서 시작해 **입력 → 상태 변경 → 그 상태를 읽는 쪽(소비자)·출력**까지 따라간다. 아래 경로를 각각 본다.

- **정상 경로** — 의도한 입력에서 의도한 결과가 나오는가
- **실패 경로** — 호출이 실패하거나 값이 비었을 때 상태가 어떻게 남는가
- **취소 경로** — 사용자가 중간에 떠나거나 취소했을 때, 늦게 도착한 결과가 현재 상태를 덮어쓰지 않는가
- **재시도 경로** — 같은 요청이 두 번 갈 때 결과가 한 번 갈 때와 같은가
- **순서가 뒤바뀐 경로** — 먼저 보낸 요청의 응답이 나중에 오면 어떻게 되는가

**변경되지 않은 쪽도 본다.** 변경이 동작을 지우거나 바꿨으면, 그 동작을 전제하는 호출자가 diff 밖에 남아 있는지 찾는다. 삭제된 가드는 diff의 `-` 줄에 있고, 그 가드에 기대던 호출자는 diff에 없을 수 있다.

탐색은 변경과 그 호출자·피호출자로 한정한다. 관련 없는 저장소 전체를 훑지 않는다. 무엇을 어디까지 찾았는지는 지적에 적는다(`00-rule.md` 00-11).

## 판정 기준

### 지적한다

1. 모든 지적은 *근거*를 갖춰야 한다. 다음 중 하나 이상: ① 구체 호출부/파일·라인 ② 트리거 사용자 행동/시나리오 ③ 사용자가 즉시 보는 잘못된 결과. 근거 없으면 보고하지 말고 질문으로 내릴 것.
2. PR 의도(title/body/diff)와 구현이 *모든 분기*에서 일치하는지 검증. 의도와 코드가 어긋난 지점이 1순위.
3. 단일 코드 위치를 넘는 *관계*까지 시야를 확장. 인접 호출자, 동시 reset돼야 할 state 필드, 동일 query 훅의 multi-callsite 인자 응집, 그리고 *같은 사실을 로컬 state·캐시·Redux·서버가 각자 들고 있어* 어긋날 수 있는 지점 등. 단 stale/desync는 둘을 어긋나게 만드는 사용자 경로를 한 문장 시나리오로 댈 수 있을 때만 보고(못 대면 Don't 1·2에 따라 질문으로 격하).
4. 컴파일/타입/문법 단계 객관 결함(미정의 상수, 누락 import, 잘못된 타입 통합 등)은 망설임 없이 보고.
5. **등급을 직접 정하지 않는다.** 두 축만 판정한다 — *영향도*는 `00-rule.md`의 닫힌 목록 다섯 항목 중 하나가 실제로 일어난다고 지목할 수 있는지, *확신도*는 해당 코드를 읽었고 이 지적의 반례가 될 방어 장치가 없음까지 함께 확인했는지(00-11과 같은 기준) 아니면 확인하지 못한 경로가 남았는지. 두 축은 서로 다른 질문이다 — 확인이 끝난 지적은 사용자 눈에 전혀 보이지 않아도 *확신 높음*이고, 그때 낮은 것은 확신도가 아니라 영향도다. 두 축을 적으면 severity는 파생표에서 따라 나온다.

### 지적하지 않는다

1. "가능성"만으로 race/stale closure/lost update 보고 금지. 트리거 사용자 행동을 명시하지 못하면 질문으로 격하.
2. stale 값/잔존 상태 보고는 *read 측을 `rg`로 확인*하기 전엔 금지. 읽는 쪽이 다시 set하거나 다른 키로 lookup하면 무관함.
3. 검증/가드 부재는 "*없을 때 무엇이 잘못 동작하는지*"를 한 문장으로 쓸 수 없으면 보고하지 말 것.
4. 라이브러리 동작/invariant(Three.js, react-query, R3F 등)는 코드/문서를 한 번 인용·검증하기 전엔 지적 금지. 표면 패턴만 보고 누수/redundant/오용 단언 X.
5. "의도 불분명"으로 보이는 코드는 단언이 아닌 *의문문*으로. 작성자가 의도적으로 다르게 했을 가능성이 있는 영역(서버 계약, UX 차별화, 점진적 마이그레이션)은 특히.

`rg`가 없는 실행 환경에서는 쓸 수 있는 검색 수단으로 같은 확인을 하고, 실제로 쓴 수단과 범위를 적는다. 확인하지 못한 경로가 남았으면 확신도를 낮춘다.

## 규칙 모듈과 같은 결함을 찾았을 때

규칙 모듈이 같은 자리를 이미 지적했어도 이 패스의 지적을 버리지 않는다. 두 지적은 근거가 다르다 — 하나는 규칙 문장, 하나는 의도와 경로다. 같은 결함인지는 이 패스가 정하지 않는다. 각자 자기 ID로 남기고, 같은 위치에 걸린 다른 지적은 서로 관련 지적으로 이어진다.

## 영향도 보정 예시

| 영향도 | 이 문서에서 자주 보이는 근거 |
|--------|------------------------------|
| 높음 | 의도한 동작이 특정 경로에서 일어나지 않아 사용자 오동작·데이터 손상·검증 실패 같은 닫힌 높은 영향 범주가 실제로 생기는 경우 |
| 낮음 | 의도와 어긋나지만 그 차이가 사용자에게 닿지 않거나, 다음 변경에서 틀리기 쉬운 상태로 남는 데 그치는 경우 |

## 반증할 때의 기준

교차검증 검증자는 이 패스의 지적을 반증할 때 아래 블록을 받는다. 규칙 조항이 없으므로 **조항 대신 이 기준과 코드 경로로** 판정한다.

이 지적은 규칙 조항이 아니라 **변경의 의도와 구현이 어긋난다**는 주장이다. `CR-{번호}`는 지적의 순번이고, 대응하는 규칙 조항은 없다 — 조항을 찾거나 지어내지 말고, 주장과 코드 경로만으로 판정한다.

반박이 성립하는 경우:

- **막는 장치가 있다** — 주장한 경로 위에 그 결과를 막는 가드·검사·정리 코드가 있다. 그 코드의 위치를 댄다
- **그 경로에 도달하지 않는다** — 주장한 입력·순서·취소가 실제 호출 구조에서 일어나지 않는다. 호출 구조를 근거로 댄다
- **전제한 의도가 다르다** — 지적이 전제한 동작이 변경의 의도가 아니다. 의도의 출처(PR 설명·요구·커밋 메시지)와 코드에서 확인한 사실을 구분해 댄다. 출처가 추정뿐이면 반박이 아니라 범위 미확정이다
- **소비자가 이미 처리한다** — 바뀐 상태를 읽는 쪽이 다시 설정하거나 다른 값으로 찾으므로 결과가 사용자에게 닿지 않는다. 읽는 쪽의 위치를 댄다

반박하지 않는 경우:

- 삭제된 가드를 지적한 주장은 **삭제 전 코드(merge-base)**를 읽고 판정한다. 가드가 사라진 것은 diff의 사실이고, 반박은 그 가드가 막던 경로를 지금 다른 코드가 막는다는 것을 보여야 한다
- 변경되지 않은 호출자를 지적한 주장은 **그 호출자가 diff 밖이라는 이유로** 반박하지 않는다. 호출자가 바뀐 동작에 기대지 않는다는 것을 그 호출자의 코드로 보여야 한다
